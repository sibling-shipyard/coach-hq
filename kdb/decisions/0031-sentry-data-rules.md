# 0031 — Sentry is the primary debug view, and it never carries coaching text

- **Status:** Accepted · 2026-08-27 · Tech Lead
- **Area:** cross-cutting (observability, web, iOS, coach-chat API)
- **Context:** Four athletes use the product. Debugging a broken experience today means asking the athlete what happened from memory. Vercel and Apple hold detailed logs, but one operator can reach them and neither is searchable from a phone. We need one debugging trail across web, API, and iOS, with a hard boundary on what it may hold.
- **Decision:** Sentry is the primary searchable debug view for web, backend API, and native iOS; Vercel and Apple logs stay as fallback sources. Events carry `operation_id`, `release`, `environment`, and `athlete_id` (the GitHub login) and nothing that identifies the athlete further. **LLM telemetry is metadata only — model name, prompt and completion token counts, and reply length in characters. The athlete's message text and the Gemini reply text are never sent to Sentry, in any field, including breadcrumbs and span attributes.** All API keys, GitHub tokens, auth headers, cookies, and secret credentials are scrubbed before capture. The iOS local timeline holds at most 200 events or 256 KiB and expires after 24 hours or on sign-out; it leaves the phone only inside a Rage Report the athlete submits, carrying only the events they selected. The Sentry organisation must be created in the EU region with retention set to 30 days; both are set-up requirements checked at account creation, not assumptions about a plan tier. The four close-friends beta athletes are treated as opted in for error monitoring; formal athlete controls come in #590. Automatic screenshots and session replay stay disabled.
- **Why:** Centralising errors in Sentry gives every operator crash, timeout, and LLM-failure visibility from a phone without console access, and `operation_id` makes a chat turn debuggable across client, function, and model. Coaching chat is the most personal data this product holds — an athlete telling Coach why they missed a week. A stack trace and a token count are enough to fix a 500; the conversation itself is not needed, and putting it in a third-party tool before the consent work in #590 exists is a liability with no debugging payoff. Capping retention at 30 days keeps enough history to triage recent releases and no more.
- **Rejected:** Capture athlete and model text on failed turns → the tempting version, and the reason this ADR is explicit: it would have made every Sentry issue a transcript, retained for 30 days, readable by every operator, with no athlete control. Reproduce from the token counts and the operation ID instead, and ask the athlete for the message when that is not enough. Build an internal log warehouse → premature for four athletes. Enable session replay → invasive, and structured timelines plus explicit Rage Reports already cover it. Wait for #590 before capturing anything → leaves the beta undebuggable for weeks.
