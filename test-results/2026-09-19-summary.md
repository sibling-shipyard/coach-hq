### How coach chat behaves now

A turn loads the athlete's repo at the latest commit, asks the model once, checks the reply with
about 22 checks, and reprompts only if one trips. It commits the validated writes atomically. A
turn makes at most four model calls: the first, one shared reprompt, one extra `workout_create`
call, and one invalid-id reprompt. If a problem survives, the athlete sees an honest "wasn't
saved" note, a missing `coach_note` gets a plain fallback, and Sentry reports what is left. The
mechanism is in `docs/eng-docs/gemini-flow.md` ("After the reprompt fails" and "Model calls per
turn, and what they cost").

**What extra calls cost.** Production runs `google/gemini-3.8-flash`, the model these tests used.
Over 360 test turns, the median turn cost $0.013, the mean $0.015, the 90th percentile $0.026 and
the maximum $0.074. The shared reprompt fired on 18 percent of 151 traced turns. Those scenarios
are built to provoke actions, so real traffic should fire it less. Four calls is about four times
one call, or $0.04 to $0.05. The retry layers share no deadline, so four slow calls could approach
the 300-second function limit.

### `fsp-end-to-end`: the First Session, start to finish

The 09-17 run used `coach-skanda-testing`'s `main`, which is past onboarding, and its script never
gave a name or date of birth, so it could not finish even on a fresh repo. On 2026-09-19 the fixture
gained a name, an exact date of birth and a coaching style, the scenario was renamed
`fsp-end-to-end`, and a `finalState` check now reads the branch after the last turn.

**First run (bug-finding), $0.058, 6/6 PASS.** The First Session completed on turn 4: `coach_since`
stamped, the pending marker cleared, a season, a main quest, a benchmark routine and a `live` week -
the pipeline itself works. Two real bugs found in that same run, filed as #1250:

1. The compiled first week had zero sessions. The run landed on a Saturday, and the compiler only
   schedules training days from today onward, so all three default days (Monday/Wednesday/Friday)
   had already passed. `data_status` was still `live`, so the harness's own check didn't catch it -
   a human read of the branch did.
2. "4 days a week" was never captured. `memory.training_availability` stayed unset, so the week
   used the default days anyway. The week's own message said "the days you said you train" about
   days the athlete never named.

**Fix and second run (verification), $0.024, 6/6 PASS - see this file's Run 2 for the full
transcript.** #1251 (a fresh PR off `main`, not stacked on this round) shipped two fixes:

1. **Late-week scheduling: fixed and confirmed.** When every stated training day has already
   passed, the benchmark now lands on tomorrow instead, with an honest message. The second live run
   confirmed this exactly: the benchmark landed on 2026-09-20 (tomorrow) with `coach_read.body`
   reading "Monday, Wednesday, Friday already passed this week, so your first session is set for
   tomorrow instead."
2. **Training-frequency capture: not fixed.** A new first-session-only guard reprompts once when the
   athlete states a frequency and nothing captures it. It fired correctly in every run, and the model
   never complied: **0 captures in 3 live runs**. Each time it wrote the frequency into `coach_note`
   (the daily log) and treated that as recorded, but only `memory_update` reaches the memory notes the
   availability parser reads. A stronger reprompt, saying `coach_note` does not count and giving a
   copy-ready value, changed nothing. In the fourth run the guard also caused a regression: the first
   pass had set the coaching style correctly, the reprompt replaced the whole reply and dropped it, and
   the First Session never completed. See Run 3 in `2026-09-19.md`. The reprompt approach is the
   wrong tool for this field.

**Root causes and the third fix round (runs 5 and 6).** Two causes sat behind the failures:

1. **A reprompt threw away the first reply's good fields.** In run 5 the first reply had the season,
   the coaching style and the timezone but no `coach_note`, so the server reprompted. The reprompt
   regenerates the reply from scratch and replaced the first one whole, so nothing was committed and
   the First Session never completed. #1252 stops reprompting for a missing note alone and carries
   the first reply's intake fields over when a reprompt omits them.
2. **Training frequency had no field of its own.** Every other intake answer does. #1254 adds
   `training_availability_update`, so it is saved like sports or style (ADR 0052).

**Run 6 (against #1254's code, $0.025): PASS 6/6, verified off the branch.** `memory.json` holds
`training_availability: {days_per_week: 4}`, the First Session completed, and the week is `live`.
The carry-over did not fire in this run, so that path is covered by unit tests only.
