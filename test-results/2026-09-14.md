**Scope decided:** Tech Lead asked vade-the-tester to give PR #823's own unchecked test-plan item
("verify on a Preview deploy against real Gemini") a live local verification instead. Tried to merge
`origin/feat/638-gemini-key-header` (`--no-commit --no-ff`) into this worktree to run its diff through
this stack's own tooling. The merge hit real, structural conflicts, not incidental ones: PR #823
branched off an older `main` before #713/#920/#1045 (this stack's history) moved Gemini calls behind
a provider-neutral `LlmAdapter` seam and relocated `geminiClient.ts`/`coachWorkoutFiles.ts` under
new directories (`_lib/gemini/`, `_lib/decide/`). Git saw those as modify/delete conflicts
(`ui/api/coach-chat/_lib/coachWorkoutFiles.ts`, `ui/api/coach-chat/_lib/geminiClient.ts`,
its test file) plus real content conflicts in `ui/api/_lib/llmAdapters/geminiSoulCache.ts` and
`ui/api/coach-message/_lib/coachMessage.ts` — the latter's conflict spans lines 876-939, where HEAD's
side calls `adapter.generate(...)` and PR #823's side is a raw `fetch` call. Reconciling that would
mean re-authoring application code inside a different abstraction than the one PR #823 was written
against — outside vade-the-tester's scope (never touches application/production code) and not a
"resolve the markers" job. Ran `git merge --abort` per the brief's stop condition, cleanly, no
leftover state (`git status` clean immediately after).

**What this makes moot:** checking `grep -rn "x-goog-api-key"` on HEAD (no merge) found the fix
already landed independently — `ui/api/_lib/llmAdapters/geminiAdapter.ts:153` and
`ui/api/_lib/llmAdapters/geminiSoulCache.ts:128` both send `x-goog-api-key` as a header today, and
`geminiAdapter.ts:3`'s own comment cites `#638`. `git log` traces this to `1b85e4b9` (#1045, ADR-driven
`askGemini` usage work) and earlier to `1329f79c`/`73df61d7` (#713's `LlmClient` seam). A repo-wide
grep for `?key=`/`generateContent\`` on HEAD found exactly 2 Gemini call sites, both header-only — no
lingering query-param usage anywhere in the current app code. PR #823 is not wrong, it's superseded:
its 4 call sites (`geminiClient.ts`, `coachWorkoutFiles.ts`, `soulCache.ts`, `coachMessage.ts`) no
longer exist in that shape on this stack: the fix is already in via a different, larger refactor.
`geminiAdapter.test.ts:54` (`"authenticates with the x-goog-api-key header, not a URL query param"`)
already covers it. One gap PR #823 would have closed that HEAD does not yet have: no test file exists
for `geminiSoulCache.ts` at all (`find ui/api -iname "*geminiSoulCache*"` returns only the source
file) — a real, small coverage gap, flagged for Bob, not fixed here.

**Environment correction to the brief:** the brief assumed a live OpenRouter call would prove the
header-auth change works end to end. It can't. `ui/api/_lib/llmAdapters/openRouterAdapter.ts:150`
authenticates with `Authorization: Bearer <key>` — a completely different mechanism from Gemini's

(`curl .../generateContent?key=$GEMINI_API_KEY` → `403`), so no live call available here can actually
exercise `x-goog-api-key` against real Gemini. Ran the OpenRouter live scenario anyway as a pipeline
smoke test (it was going to run regardless per the brief, and it's cheap) — it does not, and cannot,
